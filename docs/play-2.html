What can go wrong when you update the board?

With your partner, write at least two cases. Finish your own list before you open the hint.

Your cases

Look at BOARD.txt. What would make an update the wrong board? Write two or more cases in your own words. Do not scroll to the hint until both of you have named them.

Hint, after your own cases

  • A lowercase x or o is not a mark.
  • The digit 0 is not the letter O.
  • Others you already thought of.

The planner writes the PRD, and that role matters most.

Planner, then everyone else

A wrong PRD makes the implementer build the wrong thing. Weight the planner above the later roles.

The order of the chats

  1. Planner. Paste the planner prompt. It writes PRD.md and does not build the check.
  2. Implementer. Paste the implementer prompt. It builds only what the PRD says.
  3. Reviewer, in a fresh chat. It reads the PRD and the diff and does not edit files.
  4. Docs writer. It updates README.md and AGENTS.md so the next person can follow the project.

Planner prompt

You are the planner. Do not edit any file except PRD.md. Ask what can go wrong in BOARD.txt until the rules are settled, then write the PRD.

A legal board has exactly three rows. Each row has three cells separated by single spaces. An empty cell is a dot. A mark is the uppercase letter X or the uppercase letter O. X moves first, so the count of X minus the count of O is 0 or 1. A lowercase x or o is not a mark. The digit 0 is not the letter O. Record any other illegal cases we name.

The PRD states the checks that test_board.py and pyproject.toml must implement. It does not contain the test code. Stop when PRD.md is written.

Implementer prompt

You are the implementer. Read PRD.md and implement only that PRD. Add test_board.py and pyproject.toml so the command uv run pytest checks BOARD.txt. Do not widen the rules. Do not commit or push. Stop and show the diff.

Reviewer and docs writer

Open a fresh chat for the reviewer. Then ask the docs writer to update README.md and AGENTS.md only.

You are the reviewer, in a fresh chat. Read PRD.md and the diff. Do not edit files. Say whether test_board.py and pyproject.toml do only what the PRD says.
You are the docs writer. Update README.md and AGENTS.md so a new person can run uv run pytest and play on branch rematch. Do not change the checks or BOARD.txt.

You can watch a check fail on a broken board and pass after you restore it.

Let Copilot write the check

Copilot adds test_board.py and pyproject.toml. You run the check, break the board on purpose, and put the board back.

Run it, break it, restore it

  1. Ask Copilot, in Agent mode, to add test_board.py and pyproject.toml from the PRD.
  2. In the terminal, run uv run pytest.
  3. Break BOARD.txt on purpose: a lowercase mark, or a digit 0 where a letter O belongs.
  4. Run uv run pytest again and watch it fail.
  5. Restore the board and run uv run pytest once more.

Branch rematch starts from main on github.com, and pytest runs before every commit.

Create branch rematch

main is sacred. Don't touch it. Create rematch from main on github.com, the same way the owner created match.

Use the branch dropdown again

On github.com, open the branch dropdown and create rematch from main. Then both of you open Codespaces on rematch. Run uv run pytest before every commit on this branch.

Run the check before every commit

A pre-commit hook is a small program Git runs before it records a commit. In the Codespace, save this as .git/hooks/pre-commit and make it executable with chmod +x .git/hooks/pre-commit.

#!/bin/sh
uv run pytest

GitHub Actions can run the same tests on every push.

You can name the manifest, the lock, the runner, and the check.

Reproducibility

Someone else can rebuild the same check when the project records what it needs and the exact versions.

Four names in this project

  • Manifest: pyproject.toml says what the project needs.
  • Lock: uv.lock records the exact versions.
  • Runner: uv builds the environment and runs the command.
  • Test module: pytest runs test_board.py.

Julia records the same idea in Project.toml and Manifest.toml. R records it with renv.
