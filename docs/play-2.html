1 What can go wrong when you update the board?

With your partner or on your own, come up with at least two cases. Finish your own list before you open the hint.

Your cases

Look at BOARD.txt. What would make an update the wrong board? Write two or more cases in your own words.

Hint, after your own cases
  • X/O count difference (X moves first, so X−O is 0 or 1).
  • Lowercase x/o vs uppercase.
  • The digit 0 typed instead of the letter O (this actually happened before).
  • Plus others the pairs find themselves.

2 Grilling

The planner does this job. It matters most. A wrong agreement here makes every later role build the wrong thing.

Three ideas

PRD (product requirements document). A PRD is one document of what you are trying to achieve.

Grilling. Align the plan by letting the agent interview you.

TDD (test-driven development). Write the tests first, watch them fail, then have the agent write code until they pass.

Skills

A skill is a reusable set of prompts stored as a SKILL.md file. You do not have to retype the same instructions in every chat. The grill-me skill is one example. pstack is a bigger example: a set of skills for a whole workflow.

Paste this Grill Me prompt into the planner chat:

Interview me relentlessly about every aspect of this plan until we reach a shared understanding. Walk down each branch of the design tree, resolving dependencies between decisions one by one.

Want more? Watch Software Fundamentals for AI Coding.

Planner prompt

Stay in this same chat. Replace the cases with the ones you wrote. Paste:

You are the planner. When we update BOARD.txt, these things can go wrong:
- case 1
- case 2
- case 3 (optional)
Before writing anything, ask me one question at a time until we agree exactly which boards are valid. Then list the agreed rules as checks a test could make. Don't write code yet.

Same chat or a new chat

Keep the planner grilling and the PRD in this same chat. Start a new chat for the implementer, a new chat for the reviewer, and a new chat for the docs writer.

3 After the plan: the other roles

Each role starts in its own new chat. Paste one prompt, then read the result before you commit.

Implementer

New chat. Paste:

Write pytest tests for these rules and a pyproject.toml so `uv run pytest` works.

Reviewer

New chat. Paste:

You are the reviewer. Run `uv run pytest` and read the diff. Say what does not match the agreed rules. Do not change files.

Docs writer

New chat. Paste:

You are the docs writer. Update README.md for people and AGENTS.md for agents so both match the agreed rules. Do not change the tests.

README.md is the file for people. AGENTS.md is the file for agents and language models. It tells them how to work in this repository so they stay on the plan.

4 Reproducibility

The tests need uv, so this comes before Copilot writes them. The same setup then runs on another machine.

  • A virtual environment is an isolated set of packages for one project, so it runs the same on any machine.
  • A virtual environment manager creates it. Ours is uv.
  • pyproject.toml is the project manifest. It holds the package info, dependencies, versions, and a description. This is what you reinstall the environment from.
  • uv.lock locks the exact versions.
  • Other languages do the same thing. Julia uses Project.toml and Manifest.toml. R uses renv.

5 Let Copilot write the check

Write the tests on a feature branch, for example feature/testing. That name does not contain "match", so the branch stays off the Game Wall. Leave main unchanged.

How pytest finds tests

Tests usually live in a tests/ folder. Use one test file per function or file, named test_<name>.py, with functions that start with test_. uv run pytest finds and runs them.

Run it, break it, restore it

Create branch feature/testing from main and switch to it before these steps.

  1. Ask Copilot, in Agent mode, to add test_board.py and pyproject.toml from the PRD.
  2. In the terminal, run uv run pytest.
  3. Break BOARD.txt on purpose: a lowercase mark, or a digit 0 where a letter O belongs.
  4. Run uv run pytest again and watch it fail.
  5. Restore the board and run uv run pytest once more.
Run the check before every commit

A pre-commit hook is a small program Git runs before it records a commit. In the Codespace, save this as .git/hooks/pre-commit and make it executable with chmod +x .git/hooks/pre-commit.

#!/bin/sh
uv run pytest

GitHub Actions can run the same tests on every push.
